3.6 — app/engine/batch_evaluation.py Implementation Steps
Build order for BatchEvaluationEngine, the passive-path LLM evaluator that scores feedback batches and proposes Cypher corrections under 7 token-optimisation layers. Each step is independently testable before the next begins.
1
Extend data contracts in schemas/feedback.py
No dependencies — do this first so every later step has a typed interface to build against.
  • Add EvaluationVerdict enum: correction_needed | no_action | insufficient_evidence
  • Add BatchEvaluationItem (input) and CorrectionRecommendation (output) Pydantic models, mirroring the LLM output JSON schema field-for-field
  • Add CorrectionType enum: add_entity | update_property | add_relationship | remove_relationship
class CorrectionRecommendation(BaseModel):
    feedback_id: str
    verdict: EvaluationVerdict
    confidence: float = Field(ge=0.0, le=1.0)
    correction_type: CorrectionType | None
    target_entity: str | None
    cypher_mutation: str | None
    reasoning: str
2
Pre-batch conditional router (Layer 5)
Runs before the engine is even invoked — filters ~60% of items out of the LLM path entirely.
  • Pure function route_feedback_item(item) → Literal["auto_apply","auto_reject","evaluate"]
  • quality_score ≥ auto_apply_threshold (0.85) and inter-annotator agreement ≥ 0.90 → auto-apply, never reaches the engine
  • quality_score < auto_reject_threshold (0.20) → auto-reject
  • Everything else is queued for batching — read both thresholds from app/config.py, don't hardcode
3
Semantic dedup + batch formation (Layer 6)
Sits in FeedbackProcessor upstream of the engine — reduces item count ~40% before any LLM call.
  • Embed each feedback claim (existing FAISS embedding model), cluster with cosine-similarity threshold (start at 0.88)
  • Cluster representative carries a vote_weight = cluster size; only the representative goes into the batch
  • Chunk the deduplicated queue into batches of evaluation_batch_size (default 25, from config)
4
Shared graph context fetcher (Layers 2 & 7)
One Neo4j round-trip per batch instead of one per item.
  • fetch_graph_snapshot(entity_names: list[str]) → str — 1-hop subgraph only, via existing graph_store.py
  • Cache key: graph_ctx:{hash(sorted(entity_names))}, Redis TTL 1h
  • Reused across every batch in the same hourly cycle (Layer 7) — check cache before hitting Neo4j
  • Graceful degradation: if Redis is unreachable, fetch directly and skip caching (log a warning, don't fail the cycle)
5
Few-shot example cache (Layer 3)
Retrieved once per evaluation cycle, not once per batch.
  • get_few_shot_examples(feedback_type) → str, Redis key few_shot:{feedback_type}, TTL 24h
  • Seed the cache with a curated set of 2–3 hand-written correction examples per FeedbackType (one-time backfill script)
  • On cache miss, fall back to a static in-repo JSON fixture so the engine never blocks on Redis availability
6
Prompt assembler (Layers 1 & 4)
One system prompt, one JSON schema, amortised across all 25 items in the batch.
  • Template: system instructions + {graph_snapshot} + {few_shot_examples} + {batch_as_json_array}
  • Call LLMClient.complete_structured() with the CorrectionRecommendation JSON schema — structured output means no markdown/prose filler in the response
async def _build_prompt(self, items: list[BatchEvaluationItem]) -> str:
    entities = self._collect_entities(items)
    graph_ctx = await self.graph_ctx_cache.get_or_fetch(entities)
    few_shot = await self.few_shot_cache.get(items[0].feedback_type)
    return self.template.render(
        graph_snapshot=graph_ctx,
        few_shot_examples=few_shot,
        batch_items=[i.model_dump() for i in items],
    )
7
Core orchestration loop
BatchEvaluationEngine.evaluate_batch() — ties steps 2–6 together with retry logic.
  • Route (step 2) → dedup/batch (step 3, upstream) → assemble prompt (step 6) → call LLM → parse JSON
  • Malformed JSON response → retry once with temperature=0; second failure → route items to human-review queue
  • Async, batched via asyncio.gather across independent batches (bounded concurrency — respect LLM rate limits)
8
Cypher safety validator
Runs on every non-null cypher_mutation before it's ever persisted.
  • Deny-list check (case-insensitive, token-boundary aware — not naive substring match): DROP, CREATE INDEX, CREATE CONSTRAINT
  • Reject any DELETE not preceded by a MATCH clause in the same statement
  • Reject REMOVE on any node/property flagged compliance-sensitive in the taxonomy (risk category, jurisdiction, regulatory text)
  • On rejection: mark the recommendation verdict = insufficient_evidence, log the rejected mutation for audit — never silently drop it
9
Confidence merge + persistence
Final scoring and the write path into PostgreSQL.
  • final_confidence = llm_confidence × inter_annotator_agreement
  • Every item is stored in correction_recommendations with status = pending, regardless of confidence — the confidence gate is applied later, at application time, not here
  • Use the new PostgreSQLFeedbackClient.insert_correction_recommendation() (bulk insert for the batch)
10
Wire in and test
Integration into the orchestrator, plus the test suite that protects the token budget and safety guarantees.
  • Call from evaluation_orchestrator.py's hourly cycle, after routing produces the "needs evaluation" set
  • Add evaluation_batch_size, auto_apply_threshold, auto_reject_threshold to config.py if not already present
  • Tests: token-count assertions per band (B1 ≤250, B2 ≤500, B3 ≤800), Cypher-safety adversarial cases, malformed-JSON retry path, Redis-unavailable degradation
✅
Definition of done: a batch of 25 synthetic feedback items runs end-to-end — routed, deduplicated, evaluated in one LLM call, Cypher-validated, and persisted — with average tokens/item inside the B1–B3 bands and zero unsafe mutations reaching storage.
3.7 — Tiered Evaluation Engine (HITL Path) Implementation Steps
Build order for the four-tier ladder — routes each feedback claim to the cheapest tier that can resolve it, escalating only when necessary. Steps 1–2 and 4–6 are Phase-2-ready; Tier 1B (GNN) has two build paths, detailed at the end of this section.
1
Shared tier contract
Every tier — rule, GNN, NLI, LLM — returns the same shape so the orchestrator doesn't special-case any of them.
class TierResult(BaseModel):
    tier: Literal["1a_rule", "1b_gnn", "2_nli", "3_llm"]
    verdict: Literal["resolved", "escalate"]
    confidence: float
    evidence_ref: str | None = None
    detail: dict = {}

Also define an EvaluationTrail that accumulates every tier's TierResult for a claim — this is what gets written to evaluation_records for audit.

STEP 2 — TIER 1A · Rule Registry0 LLM tokens · runs first, always
  • Each of the 9 categories (Schema/Type, Cardinality, Referential, Temporal, Numeric, Cross-Source, Duplicate, Hierarchy, Jurisdiction) is a pure function: (claim, graph_store) → TierResult
  • Register them in a simple list/decorator-based registry so adding a 10th rule later is a one-line change
  • Run all 9 (not short-circuit) — a single fail is enough to escalate, but the full set of evidence is useful downstream
  • Reuse existing graph_store.py and entity_resolver.py — no new infrastructure
STEP 3 — TIER 1B · GNN Structural Plausibility0 LLM tokens · frozen model · see GNN options below
  • Define the interface first, regardless of which GNN option you pick: GNNPlausibilityScorer.score(subject, predicate, object, subgraph) → float
  • Ship the stub now — return a constant 0.5 so Tiers 2/3 and the orchestrator can be built and tested without blocking on GNN training
  • Swap the stub for a real implementation using Option 1 or Option 2 below — the interface contract doesn't change either way
STEP 4 — TIER 2 · NLI Evaluator~0 generative tokens · local model
  • Load cross-encoder/nli-deberta-v3-small once, as a singleton on Container in deps.py — never per-request
  • sentence-transformers is sync — wrap the inference call in asyncio.get_event_loop().run_in_executor() so it doesn't block the FastAPI event loop
  • Premise = relevant chunks from the frozen interaction_evidence snapshot; hypothesis = the feedback claim, normalised to a declarative sentence
  • Routing: entailment > 0.7 → resolved (PARTIALLY_VALID); contradiction > 0.7 or neutral > 0.7 → escalate to Tier 3
STEP 5 — TIER 3 · LLM / Agent Evaluatorcontrolled tokens · last resort
  • Build a minimal EvaluationPacket: disputed claim + top-2 evidence chunks + inconclusive rule findings + NLI score and reason — never the full conversation or full evidence set
  • Call LLMClient.complete_structured() — same call shape as batch_evaluation.py, single-item instead of batched
  • Escalate to human review when: all three tiers return confidence < human_review_threshold (0.60), the attribute is compliance-sensitive, or two authoritative sources conflict
6
Orchestrator + wiring + tests
TieredEvaluationEngine.evaluate() ties the ladder together.
  • Sequential execution, stop at first resolved verdict — never run a more expensive tier once a cheaper one is confident
  • Persist the full EvaluationTrail to evaluation_records regardless of which tier resolved it (audit requirement)
  • Call from the hourly orchestration cycle for the active HITL path, and from the passive path once auto-signals escalate an item
  • Tests: one unit test per rule category, NLI threshold boundary tests, Tier-3-escalation integration test, full-ladder golden-set regression

GNN Implementation Options (feeds Tier 1B and §4.6)

🎯
Both options implement the exact same GNNPlausibilityScorer.score() interface, so the choice is an internal swap — nothing downstream (Tier 1A/2/3, the orchestrator, the structural sweep) needs to know which one is running. Both are free to run on your existing AWS footprint — no new paid Neo4j tier or third-party ML service required.
OPTION 1 — Python R-GCN via PyTorch Geometric (more control)

Full custom relational-GCN, trained and served outside Neo4j. Best if you want control over the architecture, negative sampling strategy, and the ability to add features beyond graph topology later (e.g. text embeddings on nodes).

  1. Dependencies: add torch and torch-geometric to requirements.txt (Phase 3 only — keep out of the Phase 2 install to avoid bloating that deploy)
  2. Export training data from Neo4j: positive triples via a Cypher pull of all typed relationships; negative triples via random head/tail corruption plus any confirmed-rejected corrections accumulated in correction_execution_history
  3. Build vocab + tensors: entity2id / relation2id mappings, then edge_index / edge_type tensors for RGCNConv
  4. Model: 2–3 layer R-GCN encoder + a DistMult (or similar) scoring head over the final entity embeddings
  5. Train: binary cross-entropy over positive vs. corrupted triples, held-out validation split, early stopping — this runs as an offline job, not inside the request path
  6. Freeze & serialize: save weights to gnn_model_path (./data/models/gnn_plausibility.pt); GNNPlausibilityScorer loads this file once at process startup and never updates mid-run
  7. Inference: at score time, pull the 2-hop subgraph for the candidate triple from Neo4j (existing driver in graph_store.py), map to tensors, forward pass, sigmoid → 0–1 score
  8. A/B gate + schedule: new weights are compared against the current model on a held-out eval set before promotion; GNNRefreshJob (APScheduler) triggers weekly full retrain + daily incremental, fired by the canonical-KG-update event
class RGCNEncoder(torch.nn.Module):
    def __init__(self, num_entities, num_relations, hidden_dim=128):
        super().__init__()
        self.emb = torch.nn.Embedding(num_entities, hidden_dim)
        self.conv1 = RGCNConv(hidden_dim, hidden_dim, num_relations)
        self.conv2 = RGCNConv(hidden_dim, hidden_dim, num_relations)

    def forward(self, edge_index, edge_type):
        x = self.emb.weight
        x = F.relu(self.conv1(x, edge_index, edge_type))
        return self.conv2(x, edge_index, edge_type)
⚠️
Needs a compute target for the offline training job — a scheduled batch task on the same EC2/ECS fleet you already run on AWS is enough at AMC entity-graph scale; a GPU is a nice-to-have, not a requirement.
OPTION 2 — Neo4j GDS (GraphSAGE + Link Prediction pipeline)

Uses the free, open-source Community Edition of the Neo4j Graph Data Science library, installed as a plugin on your self-managed Neo4j-on-AWS instance. No PyTorch, no separate training infra, no Neo4j license upgrade — everything runs as Cypher procedures against the graph you already have.

  1. Install GDS Community (free): drop the GDS .jar into the Neo4j plugins/ directory on the EC2 instance, allowlist it in neo4j.conf (dbms.security.procedures.unrestricted=gds.*), restart Neo4j. No license key needed for Community Edition — it's open-source. (Note: this requires a self-managed instance; GDS Community isn't installable on AuraDB Free/Professional.)
  2. Project the graph in-memory: gds.graph.project() over the relevant node labels and relationship types, UNDIRECTED orientation (required by the link-prediction pipelines)
  3. Build a Link Prediction pipeline: gds.beta.pipeline.linkPrediction.create → add a node-property step for GraphSAGE (or FastRP as a lighter-weight fallback) → add a link-feature step (e.g. Hadamard product of the two node embeddings) → configure the train/test split
  4. Train: gds.beta.pipeline.linkPrediction.train — positive examples are existing relationships, negatives are sampled non-adjacent node pairs (mirrors the R-GCN corruption strategy); the trained model lands in the GDS in-memory model catalog
  5. Score a candidate triple: gds.beta.pipeline.linkPrediction.predict.stream against the specific node pair → probability, which maps directly onto the 0–1 output GNNPlausibilityScorer.score() already expects
  6. Wrap it: GNNPlausibilityScorer calls these procedures through the same Neo4j Python driver session graph_store.py already uses — no new client library
  7. Retraining cadence: Community Edition's model catalog is in-memory only (not persisted across a Neo4j restart), so schedule GNNRefreshJob to re-project + retrain on the same weekly/daily cadence as Option 1, rather than loading a serialized weights file
// Project + build pipeline (run once per (re)training cycle)
CALL gds.graph.project('amc-graph', '*', '*')

CALL gds.beta.pipeline.linkPrediction.create('plausibility-pipe')
CALL gds.beta.pipeline.linkPrediction.addNodeProperty(
  'plausibility-pipe', 'graphSage', {mutateProperty: 'emb'}
)
CALL gds.beta.pipeline.linkPrediction.addFeature(
  'plausibility-pipe', 'hadamard', {nodeProperties: ['emb']}
)
CALL gds.beta.pipeline.linkPrediction.train(
  'amc-graph', {pipeline: 'plausibility-pipe', modelName: 'plausibility-model'}
)

// Score one candidate triple at inference time
CALL gds.beta.pipeline.linkPrediction.predict.stream(
  'amc-graph', {modelName: 'plausibility-model',
   sourceNode: $subject_id, targetNode: $object_id}
)
⚠️
Community Edition caps GDS algorithm execution at 4 CPU cores and doesn't include the "optimized graph implementation" that Enterprise gets — fine at AMC entity-graph scale, but worth flagging as a constraint if the graph grows sharply.

Recommendation: since both share the same GNNPlausibilityScorer interface, it's low-risk to start with Option 2 (GDS) to unblock Tier 1B and the structural sweep quickly with zero new infra, then swap in Option 1 (R-GCN) later if you need finer control — the swap is contained entirely inside gnn_plausibility.py.
