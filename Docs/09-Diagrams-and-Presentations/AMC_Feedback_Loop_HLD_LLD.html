AMC Feedback Loop — Feedback, Evaluation & Self-Correction

Consolidated architecture reference — High-Level Design, Low-Level Design and engineering notes, merged from the conceptual architecture, the v2 technical design, and whiteboard working notes.

HLD — conceptual pipeline LLD — three-system technical design Every step: Input → Output v2 draft, evaluation layer subject to change

Overview

HITL feedback and agentic (no-feedback) evaluation are not two separate systems. They are two entry routes into one pipeline: Feedback → Evaluation → Diagnosis → Controlled Improvement. Every response — whether a human ever reacts to it or not — ends up in the same evidence record, the same tiered evaluation, the same diagnosis step, and the same governed correction path.

Three separate codebases implement this pipeline end to end:

  • AMC — owns the query/response flow, the feedback UI panel, and the feedback_records table.
  • Human Feedback Loop module — a separate codebase that turns one feedback_records row into one unified evaluation record.
  • Evaluation Layer — a separate system again, triggered per record, that does the deep evaluation and repair proposal (batch engine for the passive/no-feedback path, a tiered ladder for the active/HITL path).
Guiding principle: Feedback ≠ Learning. Evaluation ≠ Learning. Diagnosis ≠ Learning. The chatbot never directly learns from one user's say-so — not the knowledge graph (governed, weekly, batch-approved) and not really the LLM either, since its "learning" is a logged, confidence-scored, TTL-bound context patch rather than a parameter update. That single decision protects the system against incorrect feedback, malicious feedback, feedback poisoning, and accidental corruption of the AMC taxonomy — while still letting visible behavior improve immediately.

HLD1.3 Two Evaluation Families

Response EvaluationIs a single answer grounded, accurate, complete, current, consistent, relevant, compliant, safe, and clearly communicated?
System EvaluationRoot-cause question across three subsystems: Retrieval (recall, precision, graph path correctness, freshness), Generation (groundedness, citation use, context use, tokens), Guardrails (triggered correctly, false positive/negative rate) — a bad answer doesn't necessarily mean a bad model.
Incorrect response
   → Was correct information retrieved?      NO  → Retrieval / knowledge problem
   → Was correct evidence given to model?     NO  → Context engineering problem
   → Did model contradict the evidence?       YES → Reasoning / generation problem

HLD1.4 Correction Patch Layer vs. Canonical Knowledge Graph

Correction Patch LayerCanonical Knowledge Graph
What it isKeyed override store: disputed_node/edge → corrected_claim, with confidence, provenance, TTLThe shared ground-truth graph every user's retrieval depends on
Who writesEither resolution pathway, immediately, at a confidence tier matching how it was adjudicatedOnly the weekly Human Governance batch, after approval
EffectFast, reversible, auto-expires if never ratifiedGlobal, permanent, versioned

The LLM consults the patch layer at generation time — a context-level override, not a weight update — so the next user asking about the same disputed fact gets the corrected answer immediately, while the change stays fully logged and reversible until governance signs off on making it permanent.

LLD2.1 Three-System Technical Architecture

v2 draft. Everything downstream of AMC is decoupled by an explicit contract, not shared state:

AMC codebaseOwns query/response flow, feedback UI panel, feedback_records table
Output: identifiers only, via webhook
Human Feedback Loop moduleSeparate codebase. Input: webhook identifiers. Runs its own EvidenceAdapter to fetch the rest. Output: one unified_evaluation_records row per response
Evaluation Layer (external)Separate system, triggered per record where repair=true. Input: unified record. Output: scored/repaired findings + proposed graph mutations. Design covered in §2.5–2.6, explicitly expected to change

LLD2.2 AMC Codebase — Capture Layer

2.2.1 UI Panel

  • Rendered alongside every delivered response.
  • Issue-type checkboxes (multi-select) — Inaccurate, Incomplete, Irrelevant, Outdated, Other.
  • A feedback text box for free-form detail.
  • One Submit button — clicking it is the active-path trigger; the panel also arms the passive-path timer/blur listener the moment the response renders, regardless of whether the user ever touches it.

2.2.2 Active vs. Passive Capture — Input/Output

PathInputOutput

Passive2–4 minute window given for the user to react; window elapses with no submit, or a blur/click-away fires on the feedback box firstfeedback_records row inserted with whatever partial state exists (often nothing — response accepted silently), source='passive'

LLD2.3 Trigger to the Human Feedback Loop Module

Immediately after the feedback_records insert (either path), AMC calls the module's ingestion endpoint with just the identifiers — the module fetches the rest itself via its own read-only EvidenceAdapter, keeping AMC's payload minimal and avoiding a second source of truth for feedback content.

InputOutput
POST https://feedback-loop.internal/ingest 
{
  "session_id": "...",
  "response_id": "...",
  "source": "active" | "passive"
}
 2xx → AMC flips ingestion_status to 'sent'; non-2xx/timeout → stays/reverts to 'failed'
Decision to confirm: a webhook call can fail, or the module can be briefly down. Recommendation: AMC sets ingestion_status='pending' on insert, flips to 'sent' on a 2xx response, and a lightweight retry sweep (e.g. every 5 minutes) re-sends anything still 'pending' or 'failed' after N minutes — so a dropped webhook call doesn't silently lose a feedback row.

LLD2.4 Human Feedback Loop Module — Building the Unified Record

The module's only job: turn one feedback_records row into one unified_evaluation_records row. Six steps run in sequence, each adding to the same JSON object; nothing is persisted until the last applicable step finishes.

2.4.1 Six-Step Build — Input / Output

#StepRuns onInputOutput
1Classification (NER)Active onlyFeedback free text + issue-type checkboxesFeedbackClassification — extracted entities / issue type
2Sentiment + IntentActive onlySame feedback free textSentimentIntent — tone and intent scores

2.4.3 Record Model & Build Function

class UnifiedEvaluationRecord(BaseModel):
    session_id: str
    response_id: str
    created_at: datetime
    source: Literal["active", "passive"]
    status: Literal["pending", "in_progress", "resolved"] = "pending"
    classification: FeedbackClassification | None = None   # step 1, active only
    sentiment_intent: SentimentIntent | None = None         # step 2, active only
    evidence_pack: EvidencePack | None = None                # step 3
    enrichment: EnrichmentContext | None = None               # step 4
    diagnosis: FailureDiagnosis | None = None                  # step 5
    repair: bool = False                                        # step 6
    repair_target: Literal["vector", "graph", None] = None       # step 6

def build_unified_record(row, adapters, db) -> UnifiedEvaluationRecord | None:
    record = UnifiedEvaluationRecord(session_id=row.session_id, response_id=row.response_id,
                                      created_at=now(), source=row.source)
    # Steps 1-2 — active path only
    if row.source == "active" and row.feedback_text:
        record.classification = classify_feedback_ner(row.feedback_text, row.issue_types)
        record.sentiment_intent = score_sentiment_intent(row.feedback_text)
    # Step 3 — both paths
    record.evidence_pack = adapters.evidence.get_evidence_pack(row.response_id)
    # Step 4 — both paths
    record.enrichment = enrich_and_deduplicate(row, record.evidence_pack, db)
    if record.enrichment.is_duplicate:
        return None  # already covered by an existing cluster
    # Step 5 — both paths, degrades gracefully without classification
    record.diagnosis = diagnose_failure(record.evidence_pack, record.classification)
    # Step 6 — both paths
    repair_needed, target = analyze_repair(record.diagnosis)
    record.repair = repair_needed
    record.repair_target = target
    return record

def on_ingest(session_id, response_id, source, adapters, db):
    """Called by AMC's webhook, or by the retry sweep for a failed delivery."""
    row = db.fetch_feedback_record(session_id, response_id)
    record = build_unified_record(row, adapters, db)
    if record:
        db.write_unified_record(record)   # single write, one row per response
Trigger through to Evaluation Layer: Input — unified_evaluation_records row, status='pending'. Output — picked up independently by the external Evaluation Layer.

LLD2.5 Evaluation Layer — Batch Evaluation Engine (Passive Path)

Managed outside the Human Feedback Loop module's codebase. Triggered independently for each unified_evaluation_records row where repair = true. Scores feedback in batches of 25 under seven token-optimisation layers, and proposes graph corrections as a validated Cypher mutation rather than applying anything directly.

StageInputOutput
RouteQuality score + inter-annotator agreement per itemquality ≥ 0.85 & agreement ≥ 0.90 → auto-apply (no LLM call) · < 0.20 → auto-reject · else → queued for batching
Dedupe + BatchQueued claimsEmbedded + clustered claims (cosine ≥ 0.88); deduplicated queue split into groups of 25
Shared Context FetchBatch of 25 claimsOne Neo4j round-trip per batch (1-hop subgraph, Redis-cached 1h TTL) + a few-shot example cache (24h TTL), amortised across the batch
Assemble Prompt + LLM CallBatch + shared contextStructured output, one LLM call per batch of 25
Cypher Safety ValidatorProposed Cypher mutationDeny-lists DROP/CREATE INDEX/CREATE CONSTRAINT, rejects unguarded DELETE, rejects REMOVE on compliance-sensitive fields. A rejection is marked insufficient_evidence and logged — never silently dropped
Confidence Merge + PersistLLM confidence + inter-annotator agreementfinal_confidence = llm_confidence × inter_annotator_agreement, stored on every item regardless of score, status='pending'. The apply-time gate is a separate later decision

LLD2.6 Evaluation Layer — Tiered Evaluation Engine (Active / HITL Path)

A four-tier ladder, cheapest first. Execution stops at the first tier that resolves the claim — a more expensive tier never runs once a cheaper one is confident.

TierCostInputOutput
1A — Rule Registry0 tokensClaim + evidenceResult across 9 deterministic categories: schema, cardinality, referential, temporal, numeric, cross-source, duplicate, hierarchy, jurisdiction
1B — GNN Plausibility0 tokensCandidate tripleStructural plausibility score from a frozen model; ships as a 0.5 stub until trained
2 — NLI Evaluator~0 generative tokensClaim vs evidence (local cross-encoder)Entailment > 0.7 → resolves · contradiction/neutral > 0.7 → escalates
3 — LLM / Agent EvaluatorControlled tokensMinimal evidence packet: claim + top-2 chunks + prior tier findingsFinal verdict + confidence (last resort)
Escalates to human review when all three scored tiers return confidence below 0.60, the attribute is compliance-sensitive, or two authoritative sources conflict.

Temporal Claim Model

AMC facts are modeled with temporal validity rather than a bare current value, so a claim is fully attributable and time-boxed:

Claim
├── entity_id
├── product/plan/option
├── attribute
├── value
├── valid_from
├── valid_to
├── observed_at
├── source_id
└── source_version

e.g. a TER value is stored as TER + Scheme A + Direct Growth + value + effective period + source version — more defensible than storing only TER = X.

LLD2.8 Severity → Action Routing

Output of the verdict/graph stage is a severity-based issue type; the severity value determines how the Evaluation Layer's work queue (WQ) handles the item:

SeverityTrigger conditionRouting / action
CriticalHigh-confidence, high-impact diagnosed failureImmediate fix — bypasses the batch queue
HighConfirmed but not urgentKept in the work queue (WQ), processed as part of the next batch
LowLow confidence / low impactLogged for monitoring; not auto-escalated

NotesWhiteboard Engineering Capture

Raw working notes captured on a whiteboard during design, reconciled against the formal designs above. This is an earlier-stage sketch of the same classification → verdict → severity pipeline; several details here (e.g. a fixed "based on number of weeks at a time" cadence) were superseded by the batches-of-25 design in §2.5, and are kept here for traceability.

  • Step A — classifier: regex + GNN hybrid classifier; if confidence score < 0.8, the item is routed onward to step B rather than accepted at face value.
  • Step B — field mapping: specific version/field references noted — V-17 → response, V-18 → API — feeding an NL + claim extraction step.
  • Step C — LLM verdict: C = LLM produces a Verdict, which feeds a graph step.
  • Output: "output: severity based I.T." — i.e. the graph step's output is a severity-based issue type, matching §2.8.
  • Work queue: a WQ box (eval) receives High/Low severity items; annotated "based on no. of weeks at a time" — an early idea for time-boxed batch cadence, later formalised as fixed batch size (25) plus routing thresholds in §2.5.
  • Session/user identifiers: sketch references to session_id values and a set of UFR (user feedback record?) rows numbered 1–4, alongside a DB table sketch with columns mapping user identifiers (A, B, C) to numbered rows — an early draft of the feedback_records table in §2.2.3.
  • A note "issue type(?)" next to the DB sketch matches the issue_types column formalised in §2.2.3.

LLDAppendix — Open Decisions & Edge Cases

  • Repair locking (TBD): if the same underlying issue is flagged by multiple concurrent records while a fix is already in progress, later repair attempts need to be locked or merged against the in-flight one rather than racing it. Locking key, scope (entity-level? recipe-level?), and timeout are not yet designed.
  • Trigger delivery guarantee: the webhook-plus-retry-sweep approach in §2.3 is a recommendation, not yet confirmed — an alternative is a message queue between AMC and the module for at-least-once delivery without a custom retry sweep.
  • Evaluation Layer contract stability: §2.5–2.6 are explicitly subject to change; the one contract §2.4 depends on is the shape of a unified_evaluation_records row with repair=true and a repair_target — worth keeping stable even as the engine internals evolve.
