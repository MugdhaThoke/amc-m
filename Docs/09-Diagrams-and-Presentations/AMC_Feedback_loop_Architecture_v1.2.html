Finalized Reference Architecture

This tab presents the consolidated architecture and governing principles. The design is intentionally deterministic-first, evidence-first, compliance-aware, and LLM-last.

1. Purpose

This document consolidates the initial architecture for a governed feedback and evaluation loop for an Asset Management Company (AMC) chatbot whose backend includes:

  • Hybrid retrieval: Vector DB + Context Graph
  • Context Engineering Layer
  • AMC Domain Taxonomy
  • Guardrails and policy controls
  • Multi-source provenance and citations
  • Potential support for multiple jurisdictions such as India, US, UK, EU and others

The design goal is not to build a generic thumbs-up/thumbs-down feedback system. The intended architecture is:

Feedback → Evaluation → Diagnosis → Controlled Improvement

The design is further extended toward:

Feedback / Telemetry → Evaluation → Failure Diagnosis → RAG Health → Deterministic Repair → Validation → Controlled Healing

The system should be deterministic-first, evidence-first, LLM-last. LLMs and agents are used only where semantic ambiguity or multi-step investigation genuinely requires them.

2. Core Design Principles

2.1 Feedback is not ground truth

Human feedback is an observation or assertion. It must be preserved as raw feedback and separately adjudicated.

Example:

User feedback: "This answer is hallucinated"
        ↓
Evidence verification
        ↓
Adjudication
        ↓
Possible result:
- Supported
- Partially supported
- Unsupported
- Subjective
- Unverifiable

The underlying defect may actually be:

  • stale source,
  • wrong entity,
  • missing retrieval,
  • context-selection failure,
  • citation mismatch,
  • numerical mismatch,
  • genuine unsupported generation,
  • or no system defect at all.

2.2 Observable failure is different from root cause

A user-visible symptom such as “wrong answer” should not directly become the root-cause classification.

Observable symptom
      ≠
Technical origin
      ≠
Repair action

Example:

User symptom      : Hallucination
System diagnosis  : Stale source
Root cause        : Ingestion lag
Repair            : Source refresh + selective re-embedding

2.3 Evidence must be frozen before evaluation

Immediately after a response is generated, the system should create an immutable/versioned snapshot of:

  • user query,
  • final response,
  • retrieved evidence,
  • vector results,
  • graph paths,
  • selected context,
  • taxonomy nodes,
  • citations,
  • source versions,
  • guardrail decisions,
  • model/prompt/configuration versions,
  • system metrics.

This prevents later evaluation against changed knowledge or changed system state.

2.4 Vector DB and Context Graph are serving structures, not the ultimate source of truth

The canonical layer should remain:

Authoritative Source Plane
        ↓
Source Registry + Provenance + Version
        ↓
Derived Structures
   ├── Vector DB
   └── Context Graph

This enables self-healing by reconstruction rather than by generative reasoning.

2.5 Known problems should become code

A novel failure may initially require an LLM, agent, SME, or human investigation.

Once understood:

Novel failure
    ↓
Investigation
    ↓
Root cause understood
    ↓
Convert into deterministic rule / repair recipe
    ↓
Future recurrence handled cheaply

This is the intended learning mechanism.

2.6 AMC compliance is a first-class design dimension

The platform is not a generic RAG chatbot. It operates inside a regulated investment-management environment.

Accordingly, every response/evaluation path must be able to distinguish at least:

INFORMATIONAL CORRECTNESS
        +
INVESTOR / CLIENT COMMUNICATION QUALITY
        +
DISCLOSURE COMPLETENESS
        +
ADVICE / SUITABILITY BOUNDARY
        +
SOURCE / DOCUMENT CURRENCY
        +
SUPERVISION / APPROVAL
        +
RECORDKEEPING / AUDITABILITY
        +
PRIVACY / DATA HANDLING
        +
JURISDICTION / PRODUCT APPLICABILITY

These controls are not globally identical. The architecture therefore separates:

GLOBAL AMC CONTROL MODEL
        ↓
Jurisdiction Policy Pack
        ↓
Entity / Product / Channel / User Context
        ↓
Applicable Control Set

The core platform must remain regulator-agnostic, but every compliance decision must be jurisdiction-aware.

Current design anchors

As of August 2026, the architecture is informed by current regulator expectations and frameworks including:

  • India: SEBI (Mutual Funds) Regulations, 2026 and the 20 March 2026 Mutual Funds Master Circular; the 2026 regulatory framework emphasizes investor protection, transparency, governance and compliance architecture for mutual funds.
  • United States: SEC investment-management examination priorities continue to focus on core obligations such as fiduciary duty, standards of conduct, custody/privacy-related controls and compliance programs. FINRA's 2026 GenAI material emphasizes supervision, communications, recordkeeping, fair dealing, model reliability/accuracy, testing, monitoring and auditability where FINRA rules apply.
  • European Union: ESMA states that use of AI in investment services remains subject to MiFID II requirements including organisational requirements, conduct of business and acting in the client's best interest; ESMA highlights data quality, bias, opacity, over-reliance, privacy and security.
  • United Kingdom: FCA's 2026 AI approach relies on existing frameworks such as Consumer Duty, SM&CR and governance/control expectations, with attention to testing, monitoring, fair treatment and explanation of AI-driven decisions.

This reference design is an architecture document, not a substitute for jurisdiction-specific legal interpretation.

2.7 Prevention before detection before healing

The stress test adds a stronger operating principle:

Prevent where deterministic invariants can prevent; detect cheaply where prevention is impossible; reason only where ambiguity remains; heal only where the repair is evidence-backed, bounded, reversible and permitted.

Therefore the preferred order is:

PREVENT
   ↓ if not preventable
DETECT
   ↓
CONTAIN
   ↓
DIAGNOSE
   ↓
REPAIR ELIGIBILITY
   ↓
VALIDATE
   ↓
CONTROLLED HEAL

3.1 Synchronous vs asynchronous evaluation

Not all evaluation should sit in the user-response critical path.

Synchronous critical intercept

Only cheap, high-confidence, high-impact controls should block delivery:

wrong canonical scheme/entity ID
deterministic numerical mismatch
missing mandatory disclosure
non-existent/broken required citation
known prohibited wording
jurisdiction/product hard restriction
PII/data-handling violation detectable by rule
system says required authoritative evidence is absent

Asynchronous evaluation

Use after delivery for:

semantic completeness
citation entailment
implicit suitability/advice boundary
tone nuance
complex factual synthesis
root-cause attribution
incident correlation
RAG health investigation
quality sampling

This preserves response latency while allowing strong supervision.

    MISSING
    CONFLICTING
    TEMPORALLY_UNCERTAIN

Every EvaluationPlan should carry an execution budget:

  LLM budget = small / bounded

Normal response with no anomaly:
  LLM budget = 0

  larger evidence budget

3.4 Failure observation vs incident

A failure is an observation. Repeated correlated failures may be one incident.

FailureObservation
       │
       ▼
Correlation Engine
       │
       ├── source/version
       ├── taxonomy node
       ├── model/prompt version
       ├── vector index build
       ├── graph build/edge
       ├── jurisdiction/policy pack
       ├── product/scheme
       └── time window
       │
       ▼
Incident

Example:

643 wrong responses
       ↓
all depend on source_version = 17
       ↓
version 18 ingestion failed
       ↓
ONE INCIDENT
       ↓
ONE ROOT REPAIR

This prevents hundreds of duplicate improvement tickets.

3.5 Repair eligibility

A confirmed defect is not automatically eligible for self-healing.

Confirmed Root Cause
       ↓
REPAIR ELIGIBILITY
       │
       ├── source-provable?
       ├── deterministic?
       ├── reversible?
       ├── bounded blast radius?
       ├── validation available?
       ├── provenance preserved?
       ├── compliance impact understood?
       └── policy permits automatic change?

Repair classes:

Class Meaning Example Default action
R0No repairinvalid feedbackclose / monitor
R1Auto-safe mechanicalmissing embeddingautomatic repair + verify
R2Auto + shadowstale graph edge with authoritative replacementrepair in shadow + promote if tests pass
R3Approval requiredtaxonomy/policy structural changegovernance approval
R4Investigativeconflicting authoritative sourcesagent/SME investigation
R5Prohibited auto-repairambiguous regulatory interpretationhuman/compliance only

3. Quick Reference — Main Control Principles

Design Principle Meaning in Practice
Deterministic-first Use rules, provenance, schemas, numeric checks, temporal checks and graph/index diagnostics before semantic or LLM evaluation.
Evidence-first Freeze Interaction Snapshot and EvidencePack before evaluation; do not let evaluators recreate truth from changing system state.
Compliance-aware Mandatory AMC/regulatory controls always run when applicable; they are not sampled away for cost reasons.
Minimum sufficient evaluation The Adaptive Router chooses the cheapest reliable evaluator path and stops once authoritative evidence becomes decisive.
Incident-aware Repeated correlated failures become an incident so the system avoids paying repeatedly for duplicate diagnosis.
Governed self-healing Only evidence-backed, bounded, reversible and policy-permitted fixes are eligible for automated/shadow repair.

Deterministic first

Semantic involvement

Use semantic evaluation only when the communication itself must be interpreted, for example:

  • whether an apparently neutral comparison is promotional,
  • whether a response creates an implied guarantee,

The same sentence can have different regulatory significance depending on:

  • who says it,
  • to whom,
  • about what product,
  • in which jurisdiction,
  • in what channel,
  • and whether the system is providing information, advice, promotion or execution support.

19. Why Deterministic-First?

Advantages

  • near-zero token consumption,
  • predictable latency,
  • repeatable outcomes,
  • explainable decisions,
  • auditable evidence,
  • easier compliance review,
  • easier regression testing,
  • lower evaluator hallucination risk,
  • simpler cost control.

Limitations

  • rules can become brittle,
  • implicit meaning is difficult,
  • taxonomy maintenance required,
  • rule explosion is possible,
  • jurisdiction-specific logic must be versioned,
  • false negatives can occur in nuanced language.

Design response

Do not choose deterministic instead of semantic intelligence.

Use a cascade:

Can rules establish the answer?
        YES → STOP

Can a cheap semantic model resolve it?
        YES → STOP

Does an LLM materially improve confidence?
        NO → STOP

Does evaluation require actions/multi-step investigation?
        NO → do not use Agent

Only then:
        Agent / Human

34. Explicit Stop Rules

Cost control depends heavily on stopping escalation.

STOP-1 — Deterministic proof

+ exact entity
+ exact temporal context
+ deterministic mismatch

→ verdict established
→ STOP

No semantic model, LLM, or agent required.

STOP-2 — Evidence absent

required evidence missing
+ deterministic recovery unavailable

→ UNVERIFIABLE
→ STOP factual adjudication

Do not ask an LLM to manufacture a verdict.

STOP-3 — Known incident

observation matches active confirmed incident
+ same causal signature

→ attach to incident

STOP-4 — Semantic model resolves within calibrated confidence

semantic/NLI output

+ confidence ≥ approved threshold

→ STOP

policy says HUMAN_REQUIRED

→ route to compliance/HITL

Component 7 — Adaptive Evaluation Router

The Router is a deterministic, policy-driven orchestration engine. It selects the minimum sufficient evaluation using applicability, mandatory controls, evidence sufficiency, incident state, signal dimensions, and explicit token/latency budgets.

29. Adaptive Evaluation Router — Design Baseline

29.1 Purpose

The Adaptive Evaluation Router determines:

What needs to be evaluated, by which mechanism, at what depth, under which AMC/regulatory context, and within what cost/latency budget.

The Router is not itself the factual judge, compliance judge, LLM agent, or repair engine.

It is a policy-driven orchestrator.

Preferred implementation principle:

Deterministic Policy / State Engine
        +
Calibrated Statistical Signals
        +
Optional Semantic Signals
        ↓
EvaluationPlan

Avoid:

LLM decides what to evaluate
        ↓
LLM decides which agents to call
        ↓
Agents decide whether more agents are needed

The second pattern creates unnecessary nondeterminism, token multiplication, latency, and audit difficulty.

29.2 Router Design Principles

P1 — Mandatory controls cannot be sampled away

Cost optimization may reduce evaluation depth, but must never bypass an applicable hard AMC/regulatory control.

Applicable Mandatory Control
        >
Cost Optimisation
        >
Sampling Policy

Examples may include, depending on jurisdiction/product/channel/policy:

  • mandatory disclosure presence,
  • hard product eligibility restrictions,
  • deterministic numeric reconciliation,
  • required source/current-document validation,
  • privacy/data handling hard rules,
  • advice/suitability escalation requirements,
  • record/evidence capture requirements.

P2 — Adaptation means minimum sufficient evaluation

The Router should select the least expensive reliable capability that can resolve the question.

Rule can prove it?
    → use rule and STOP

Rule cannot prove it, but semantic classifier can?
    → use semantic classifier and STOP

Material ambiguity remains?
    → bounded LLM

Evaluation requires multi-step evidence acquisition?
    → Agent

High-impact unresolved regulatory issue?
    → Human / Compliance

P3 — Evidence sufficiency precedes reasoning

If required evidence is missing, the Router should prefer deterministic recovery or an UNVERIFIABLE state.

Do not ask an LLM to infer truth from incomplete evidence.

P4 — Regulatory applicability is part of routing context

The same sentence may have different significance depending on:

jurisdiction
regulated entity
product
customer/client type
channel
information vs advice mode
execution context
policy-pack version

Therefore:

Interaction
    ↓
ApplicableControlSet
    ↓
Router

not:

Interaction
    ↓
Generic evaluator
    ↓
Compliance check later

P5 — Active incidents should short-circuit repeated diagnosis

If a new failure matches a confirmed active incident:

new observation
    ↓
incident match
    ↓
known root cause
    ↓
attach observation
    ↓
skip repeated expensive diagnosis

This can materially reduce LLM/agent usage during systemic failures.

P6 — Every routing decision is auditable

The Router must persist why it:

  • selected an evaluator,
  • skipped an evaluator,
  • stopped escalation,
  • exceeded a default budget,
  • required human escalation,
  • or attached the event to an existing incident.

34. Explicit Stop Rules

Cost control depends heavily on stopping escalation.

STOP-1 — Deterministic proof

+ exact entity
+ exact temporal context
+ deterministic mismatch

→ verdict established
→ STOP

No semantic model, LLM, or agent required.

STOP-2 — Evidence absent

required evidence missing
+ deterministic recovery unavailable

→ UNVERIFIABLE
→ STOP factual adjudication

Do not ask an LLM to manufacture a verdict.

STOP-3 — Known incident

observation matches active confirmed incident
+ same causal signature

→ attach to incident
→ STOP repeated root-cause investigation

STOP-4 — Semantic model resolves within calibrated confidence

semantic/NLI output
+ within validated domain
+ confidence ≥ approved threshold

→ STOP

STOP-5 — Compliance rule requires human decision

policy says HUMAN_REQUIRED

→ STOP automated adjudication
→ route to compliance/HITL

The LLM may assist with evidence summarisation, but should not replace the required human decision.

47. Router Pseudocode

Illustrative logic:

function route(ctx):

    controls = resolve_applicable_controls(ctx)

    plan = new EvaluationPlan()

    plan.add(mandatory_deterministic_controls(controls))

    if critical_hard_failure(plan):
        return SAFE_ACTION_OR_HOLD

    evidence = assess_evidence(ctx)

    if evidence == MISSING:
        if deterministic_recovery_available(ctx):
            plan.add(EVIDENCE_RECOVERY)
        else:
            return UNVERIFIABLE

    if evidence == CONFLICTING:
        return CONFLICT_WORKFLOW

    incident = match_active_incident(ctx)

    if incident.confident_match:
        return ATTACH_TO_INCIDENT

    hypothesis = classify_failure_signals(ctx)

    capabilities = capability_registry.lookup(
        hypothesis,
        controls,
        evidence,
        budget=ctx.budget
    )

    for capability in capabilities:

        result = execute(capability)

        if result.is_decisive and stop_rule_allows(result, controls):
            break

        if budget_exhausted():
            return SAFE_UNKNOWN_OR_ESCALATE

    if material_ambiguity_remains():
        if bounded_llm_allowed():
            execute(LLM_JUDGE)

    if multi_step_investigation_required():
        if agent_allowed():
            execute(AGENT)
        else:
            escalate(HUMAN)

    return EvaluationPlan + RouterDecision

The actual implementation should be policy/state-driven, not hard-coded as a monolithic function.

50. Router Architecture Decision Record

Decision

Use a deterministic, policy-driven Adaptive Evaluation Router.

Why

  • lower token consumption,
  • lower latency,
  • reproducibility,
  • auditability,
  • explicit mandatory-control coverage,
  • regulator/jurisdiction policy integration,
  • easier incident reuse,
  • predictable failure behaviour.

Why not an LLM Router

An LLM Router introduces:

  • nondeterministic evaluator selection,
  • possible mandatory-control omission,
  • difficult reproducibility,
  • additional token cost,
  • harder auditability,
  • susceptibility to prompt/context variation.

An LLM may inform a signal such as implicit intent, but should not own the routing policy.

51. Result of the 15-Scenario Stress Test

The stress test supports the Router concept with several refinements:

  1. Mandatory controls must be separated from sampled quality evaluation.
  2. Safe fallback is often preferable to a blocking LLM chain for high-risk ambiguity.
  3. Conflict detection should produce a conflict state, not force an automated verdict.
  4. Active incidents should short-circuit duplicate diagnosis.
  5. Evaluator selection must be capability-based, not agent-based.
  6. Budget and stop rules are first-class controls.
  7. Router decisions require full versioned audit logs.
  8. Policy-pack changes and model changes should automatically alter sampling policy.
  9. The Router itself must be regression-tested as a governed component.
  10. Mature operating cost should fall as recurring failures convert into deterministic rules.

Component 9 — Failure-Attribution Graph

The failure graph is operational/causal intelligence and is deliberately separate from the user-facing Context Graph. Raw feedback and unverified hypotheses must never become answer-serving truth.

72. Failure-Attribution Graph — Purpose

The existing Context Graph serves the chatbot's domain/retrieval needs.

The Failure-Attribution Graph should be logically separate.

Do not indiscriminately merge operational failure data into the user-facing Context Graph.

Preferred architecture:

DOMAIN CONTEXT GRAPH
   user-answering knowledge
          │
          │ shared canonical IDs
          ▼
FAILURE-ATTRIBUTION GRAPH
   evaluation / causal evidence

They may reference the same:

source_id
scheme_id
taxonomy_node_id
policy_control_id

but should have separate access policies and serving behavior.

73. Why Separate the Failure Graph?

If failure/evaluator data is inserted directly into the production context graph:

  • operational noise may leak into retrieval;
  • user responses may retrieve internal diagnostic conclusions;
  • unverified failure hypotheses may contaminate domain knowledge;
  • feedback poisoning could affect answer generation;
  • graph maintenance becomes harder;
  • retention/access-control requirements differ.

Therefore:

Failure intelligence should inform routing/healing, not become answer evidence by default.

24. Architectural Deductions

Deduction 1

The EvidencePack is more fundamental than the LLM evaluator.

Without evidence provenance, all later evaluation becomes less reliable.

Deduction 2

The primary unit of evaluation should often be claim-level, not whole-response-level.

Deduction 3

A failure taxonomy should not stop at “hallucination / tone / citation / intent.”

It needs:

Symptom
+ Subtype
+ Detection method
+ Root cause
+ Severity
+ Healing action

Deduction 4

Self-healing is primarily a state-reconciliation and reconstruction problem, not an agentic reasoning problem.

Deduction 5

Every novel failure should be evaluated for conversion into:

  • a rule,
  • a constraint,
  • a health metric,
  • a repair recipe,
  • or a regression test.

Deduction 6

The mature system should become less dependent on LLM evaluation over time, not more.

26. Initial Success Criteria

The first implementation should demonstrate:

  1. Every response has an auditable InteractionSnapshot.
  2. Every evaluation uses a frozen EvidencePack.
  3. Human feedback is preserved separately from adjudicated truth.
  4. Failure categories distinguish symptom from root cause.
  5. Deterministic checks resolve the majority of simple cases.
  6. Semantic/LLM evaluation is invoked selectively.
  7. Evaluation cost is measured per interaction and per true failure.
  8. Confirmed failures enter a controlled improvement queue.
  9. No user feedback directly mutates production knowledge.
  10. Known RAG failures can map to deterministic repair recipes.
  11. Repairs are validated in shadow before promotion.
  12. The architecture can later accept AMC taxonomy, jurisdiction packs, and an adaptive router without redesign.

27. Final Design Position

The target is not an “agentic feedback system.”

The stronger architecture is:

A governed evaluation and repair control plane that uses deterministic evidence, domain structure, semantic models, LLMs, agents and humans in descending order of economic preference and ascending order of ambiguity.

The long-term objective is:

100% Observable
      ↓
100% Cheaply Inspectable
      ↓
Most Problems Deterministically Classifiable
      ↓
Known Problems Automatically Repairable
      ↓
Ambiguous Problems Escalated Selectively
      ↓
Every Validated Failure Improves Future Rules

The intended outcome is a feedback/evaluation system that becomes more explainable, more deterministic, more compliance-aware and less token-dependent as it matures.

Raw feedback never becomes answer knowledge directly.

Every significant taxonomy/policy/repair change runs cross-layer regression.

Versioned lineage from interaction to control to failure to repair is a core platform capability.
