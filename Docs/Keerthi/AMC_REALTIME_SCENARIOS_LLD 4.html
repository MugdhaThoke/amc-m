Active vs Passive — How the Loop Differs

Every interaction produces a frozen EvidencePack the moment a response is delivered. What happens after that delivery splits into two paths depending on whether the user speaks up. Both paths ultimately feed the same evaluation, diagnosis, and repair engine — they just arrive with different signal richness.

🟣

Active Scenario

The user explicitly submits feedback — a thumbs-down, a category selection ("Hallucination", "Wrong NAV"), a highlighted span, or free text. This is a direct signal with high specificity but low volume (~5–15% of interactions).

What the system gains
  • ✅ Specific failure category from user
  • ✅ Highlighted span pointing to wrong sentence
  • ✅ Free-text correction ("NAV should be ₹42.18")
  • ✅ Actor role (end-user vs compliance officer vs SME)
  • ✅ High-value signal for entity + correction extraction
Trigger path
POST /api/feedback → NER + Sentiment → Quality Score → Evaluation Queue
🔵

Passive Scenario

The user says nothing. The system captures session telemetry, retrieval metrics, source health signals, and structural checks automatically on every interaction — 100% coverage with zero user burden.

What the system gains
  • ✅ Source version vs index version mismatch
  • ✅ Retrieval confidence scores and empty-retrieval flags
  • ✅ Citation integrity (exists? resolves? matches span?)
  • ✅ Numeric extraction vs canonical source comparison
  • ✅ Context truncation, tool failure, latency anomalies
Trigger path
Auto-signal on every response → D2 metrics → E0/E1 deterministic checks → anomaly flag if triggered

⚖️ Adjudication — Multi-Dimension VerdictAsync · Zero LLM
Adjudication output — per dimension

🎯
Why adjudication is per-dimension, not a single score: The citation dimension is PARTIAL (not FAIL) because the citation link is valid — it's the model that failed to use the cited value. If we collapsed everything to one score, we'd misclassify this as a citation failure and repair the citation pipeline. The actual failure is generation (the model didn't copy the cited value correctly) — a completely different repair target.

R4 — Investigative

R5 — Prohibited Auto-Repair
When it fires
Repair requires interpreting a regulatory rule, a suitability standard, or a jurisdiction applicability decision. These are legal/compliance determinations — never autonomous.

LLM role: May summarise the conflict. Must not make the regulatory determination.

When it fires
Feedback is invalid, duplicated, or system behaved correctly. The complaint is about user preference, not a system defect.

The 5 Distinctions That Prevent Wrong Repairs

1️⃣
F07 Hallucination vs F05 Stale Source
F07: Model generated value not in any retrieved chunk. Response says 38%, all chunks say 14.2%. Detection: response_number ∉ chunk_numbers. Fix: prompt regression.

F05: Model correctly copied a stale value. Response says 0.79%, chunk says 0.79%, but canonical source now says 0.82%. Detection: source_version_used ≠ canonical_current_version. Fix: re-ingest source.

Confusing these → wrong component blamed, wrong team investigates, same error recurs.
2️⃣
F09 Context Drop vs F04 Retrieval Miss
Context Drop: Chunk was retrieved (appears in FAISS top-K) but dropped at reranking stage. Visible in D2.evidence_rejected[]. Fix: reranker threshold rule.

Retrieval Miss: Chunk was never retrieved — not in top-K at all. Fix: re-embedding, index update, or BM25 rule.

Confusing these → months of re-indexing work when the actual fix is a one-line reranker threshold rule.
3️⃣
F06 Citation Integrity vs Citation Entailment
Integrity: Does the citation link exist and resolve? Deterministic check (E1). Fix: citation pipeline repair.

Entailment: Does the cited content support the claim? Semantic NLI check (E3, ~0 generative tokens). Fix: retrieval ranking rule, forced-include, or pre-delivery gate.

Treating both as "citation problem" sends integrity fixes to the wrong pipeline and misses entailment failures entirely.
4️⃣
Feedback as Claim vs Feedback as Ground Truth
Claim: User says "TER should be 0.82%". This is a hypothesis. The system verifies it against the canonical source (AMFI_v18). If the canonical source confirms 0.82%, the feedback is supported.

Ground Truth (wrong): Directly updating the graph with user-asserted value. Could cause feedback poisoning — a competitor or malicious actor submitting false corrections at scale.

The verification step is non-negotiable. It is what separates a governed improvement loop from a feedback-poisoning vulnerability.
5️⃣
Isolated Failure vs Incident (Root Shared)
Isolated: One response with a wrong value. One user reported it. Root cause may be local (single entity, single chunk problem).

Incident: 20+ responses share the same failure signature (same source version, same model version, same chunk). One investigation, one repair. Without incident correlation: 200 individual LLM evaluations. With it: 1 investigation + 199 STOP-3 short-circuits.

Incident awareness is the single biggest cost control mechanism in the evaluation loop.
✅
Factuality vs Compliance — Independently Scored
A response can be: factually correct but non-compliant (correct TER, missing SEBI risk disclosure) or compliant but factually wrong (all disclosures present, but TER value is stale).

Both dimensions are evaluated independently. A single "quality score" would mask which dimension failed. C03 (Factual Accuracy) and C07 (Disclosure) are separate control families for exactly this reason.

Combined scores hide regulatory failures behind factual passes and vice versa.
